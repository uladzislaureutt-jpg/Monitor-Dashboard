# Monitor 0.5 — настройка сетевой «Рабочей комнаты»

## Что хранится на сервере

Только небольшие данные совместной работы:

- сообщения и объявления;
- имя автора;
- время сообщения;
- при выборе «Обсудить» — заголовок и URL публикации.

Архив мониторинга, SQLite, выдержки, категории, география и dashboard-bundle на сервер «Рабочей комнаты» не отправляются.

## Почему Supabase

Для группы из 5–7 пользователей достаточно одного небольшого управляемого Postgres-проекта. Приложению нужен только Project URL и публичный `publishable/anon` key. `service_role` в приложение вводить нельзя.

## Первичная настройка администратором

1. Создайте отдельный проект Supabase.
2. Откройте SQL Editor и выполните целиком `backend/supabase/workroom.sql`.
3. В Authentication → Users создайте 5–7 пользователей с электронной почтой и паролем. Пользователей лучше создавать администратору, а публичную самостоятельную регистрацию отключить.
4. В Table Editor → `monitor_profiles` задайте нормальные `display_name`. Для одного пользователя можно поставить `is_admin = true`; он сможет удалять сообщения других пользователей.
5. В настройках проекта скопируйте:
   - Project URL;
   - Publishable key (или legacy anon key).
6. Не копируйте и не раздавайте `service_role` key.

## Настройка каждого компьютера

1. Откройте «Рабочая комната» в левой панели.
2. Введите Project URL, Publishable/anon key и ключ комнаты `sep-monitor`.
3. Нажмите «Сохранить подключение».
4. Войдите под личной почтой и паролем.

Параметры проекта сохраняются локально. Пароль не сохраняется: после входа приложение хранит локально только refresh/access session Supabase. При выходе session удаляется.

## Как работает обмен

- новые сообщения проверяются примерно раз в 20 секунд;
- при отсутствии сети показывается последний локальный кэш сообщений;
- объявления закрепляются вверху;
- непрочитанные сообщения показываются числом на кнопке «Рабочая комната»;
- в карточке публикации есть кнопка «Обсудить» — она открывает комнату и прикрепляет заголовок + ссылку;
- локальные заметки, созданные в 0.4.x, не удаляются и могут быть опубликованы по одной.

## Безопасность

RLS разрешает чтение только аутентифицированным пользователям. Сообщение при записи всегда привязывается к `auth.uid()` серверным trigger-ом, поэтому клиент не может выдать себя за другого автора. Удалять можно свои сообщения; администратор может удалять любые.

0.5 рассчитана на один доверенный коллектив. Если позже понадобятся несколько независимых групп в одном backend, следует добавить membership-таблицу и room-level RLS.
